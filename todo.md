# OpenSend implementation TODO

Scope decisions recorded 2026-09-08 after reviewing the Paper UI. These are planned changes, not completed functionality. See [SES reference hub](docs/aws-ses/README.md) and [implementation decisions](docs/aws-ses/implementation-decisions-and-verification.md).

## Initial build

- [ ] **Environment-configured AWS connection.** Configure the server's AWS credentials and permitted sending regions through deployment configuration. Standard explicit credential variables are `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional `AWS_SESSION_TOKEN`, and `AWS_REGION` for the default region. Prefer an attached workload role when hosted on AWS; do not require static keys. Keep the allowed-region list and per-region configuration sets in server configuration, not caller-controlled arbitrary endpoints. Validate the actual account and regional readiness at startup/refresh. Do not expose secrets to the browser or commit an environment file. A pasted temporary session token needs renewal; environment variables do not themselves supply an STS refresh workflow. This initial connection is deployment-managed, not a multi-customer credential-enrollment system. [AWS credential provider reference](https://github.com/aws/aws-sdk-js-v3/blob/main/packages/credential-providers/README.md).
- [ ] **Retention that supports the designed segments.** Retain individual email logs, rendered message content, detailed provider events and webhook attempt details for 30 days. Maintain minimal per-contact engagement timestamps and observation-coverage metadata while the contact exists, so 90-day inactivity rules do not require retaining old email bodies. Retain consent/suppression state independently; deleting logs must not re-enable marketing or erase opt-outs. Campaign drafts and their current attachment assets are not send logs and must remain usable. Cleanup must respect shared assets and queued jobs.
- [ ] **SES-compatible personalization.** Replace the illustrated Liquid-style `{{first_name | default: "there"}}` syntax with SES-compatible placeholders such as `{{first_name}}`. Apply a configured fallback to replacement data before submission. Use the documented stored-template Handlebars capabilities only where supported; inline templates support simple substitutions. Escape untrusted HTML substitutions and validate URLs. Save immutable campaign content revisions internally; no template-library screen is needed for launch.
- [ ] **Full internal event coverage and selectable outgoing webhooks.** Ingest all ten relevant SES event types: send, delivery, bounce, complaint, reject, delivery delay, rendering failure, open, click and subscription. Capturing open/click events requires tracking to be enabled for that stream; use marketing tracking for engagement segments, with explicit controls, and leave transactional tracking off by default. Offer all ten categories in the webhook selector. Default new endpoints to the seven delivery/processing categories (the existing six plus rendering failure); engagement and subscription notifications are opt-in. Local hosted unsubscribe changes must also produce a consent/subscription event—SES will not report an application-owned preference change automatically. Normalize and deduplicate both sources. Exclude known `isBotEvent=Likely` interactions from default engagement segments, preserve unknown classifications, and never describe the remainder as proven human activity.
- [ ] **Non-sending test API keys.** `os_test_` requests validate inputs and exercise a separate simulated message lifecycle without calling SES to send, submitting live render/validation requests, or changing real consent/suppression. Label responses, logs and any test webhook payloads as test/simulated; never present synthetic delivery as observed SES delivery. Keep test data out of production metrics and engagement segments. Do not post test events to live webhook subscriptions automatically; explicit endpoint testing is separate. The campaign editor's real “Send test” uses the configured live connection with an explicit test recipient and normal AWS charges/limits.

## Attachments and unsubscribe

- [ ] **Campaign attachment controls.** Add file selection/upload and removal, show filename/type/size and upload/validation status, and carry attachments through draft save, preview/review and real test send. Prevent scheduling while an upload is incomplete or invalid. Version attachment references with campaign content so later edits cannot change an already scheduled message. Store files privately, with workspace ownership checks and controlled retention; do not expose public storage URLs by default.
- [ ] **Transactional API attachments.** Support binary attachment data represented appropriately at the API boundary, filename and optional content type; support inline-image disposition/content-ID where needed. Validate file restrictions and final encoded MIME size, not just raw upload size. SES v2's 40 MB message ceiling includes content, encoding and MIME overhead; do not offer a 40 MB raw attachment allowance. Do not fetch arbitrary attachment URLs in the first implementation. Bulk attachments are shared across a batch; distinct personalized files require separate sends or compatible grouped batches. See [sending reference](docs/aws-ses/sending-and-templates.md).
- [ ] **Hosted one-click footer unsubscribe.** A recipient clicks “Unsubscribe” and is immediately opted out of all marketing for that workspace across its sending regions, then sees a hosted success page. No login or second confirmation. Use an unguessable authenticated opaque token, not a raw email address as authorization. Apply the change idempotently and recheck consent for queued-but-not-dispatched sends. Never remove hard-bounce/complaint suppression or block essential transactional mail solely because of a marketing opt-out. Use a configured public HTTPS base URL, not an untrusted request Host header.
- [ ] **Mailbox-provider one-click unsubscribe.** Also emit `List-Unsubscribe` and `List-Unsubscribe-Post` and process the RFC 8058 POST route. The hosted footer action is distinct from the provider POST mechanism. Direct footer navigation is intentionally state-changing to satisfy the requested one-click behavior; automated link scanners following it can trigger opt-outs. Do not claim HTTP GET safety or scanner-proof human detection. A confirm-button page would mitigate that risk but is not the selected experience. Validate actual delivered headers/DKIM coverage and protect tokens from logs, analytics and referrer leakage.
- [ ] **Unsubscribe edge cases.** Repeated valid clicks remain successful; invalid/tampered tokens do not disclose contact existence; opt-outs apply before pending campaign dispatch and survive imports/log cleanup. Do not automatically expire valid unsubscribe capability merely because a campaign is old. Provide no automatic re-subscribe on success. If the existing “Manage preferences” footer link has no destination at launch, omit it rather than shipping a dead link; a topic/list preference center is deferred.

## Verification gates

- [ ] Exercise configured account/region permissions with an authorized real SES account; record which send modes and event paths actually work. Do not call docs, local preview or simulated test keys a live integration test.
- [ ] Verify a 90-day inactive segment using retained engagement summaries and coverage metadata after 30-day detail expiry; newly imported contacts with unknown history must not be labeled inactive for 90 days.
- [ ] Verify rendering failure, subscription changes, bot classifications, duplicate/out-of-order events and outgoing webhook opt-in/default behavior.
- [ ] Verify attachment persistence, ownership, encoded-size rejection, batch sharing and decoded recipient MIME with safe files.
- [ ] Verify the hosted footer and RFC 8058 paths, queued-send consent checks, repeat requests and invalid-token privacy. Test keys must never send via SES or mutate production data.
