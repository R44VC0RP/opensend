# MX credential review — 2026-11-05 (proposal, not for deployment)

**Release blocker: creating arbitrary customer identities with an immutable ownership tag.** `operations.ts:289` already passes `Tags` inside `CreateEmailIdentity`; there is no separate SDK tagging call to remove. [SES's API-to-action mapping](https://docs.aws.amazon.com/service-authorization/latest/reference/list_sesv2.html#list_sesv2-operation-CreateEmailIdentity) lists both `ses:CreateEmailIdentity` and `ses:TagResource`. `aws:RequestTag` and `aws:TagKeys` restrict the key/value, **not the operation that requested the tag**. The first tag on an existing untagged identity has the same documented tag context as the dependent authorization on a new identity. Requiring the existing tag to be absent does not distinguish them. The simulator allowed the proposed key/value/absent-existing-tag restriction on an unrelated untagged identity. That would also unlock deletion, MAIL FROM and tenant association. Do not grant it.

The shared draft fails closed: it allows tagged `CreateEmailIdentity` but denies its separate identity-tag authorization. BYO v5 retains v4's idempotent-only tag permission (request value must equal an existing claim); it cannot add a claim to an untagged identity either. **Do not treat the primary action's Allow as evidence that domain creation works.** There is no documented SES equivalent to `ec2:CreateAction`. A separately trusted provisioner that accepts only create-if-absent and never exposes tagging credentials to the Worker is one way to meet both requirements. That is an architecture and deployment decision, not a policy-simulator fix.

## Verification — not all green

The initial files matched the default customer-managed policy version and the published v4 template. With the actual 12 digits substituted, the candidate shared policy has **6,126 / 6,144** non-whitespace characters, **46 explicit Allow actions** and no wildcard Allow actions. Four v5 actions are gone: `ses:ListEmailIdentities`, `ses:DeleteReceiptRule`, `s3:ListBucket`, `s3:PutBucketOwnershipControls`. Identity-level `ses:TagResource` is also gone; configuration-set create still needs that action. BYO removes `ses:SendRawEmail` and `s3:PutBucketOwnershipControls` and keeps `s3:ListBucket` only with receiving enabled in Virginia.

AWS `iam simulate-custom-policy` returned **623 action/resource/context decisions in 331 requests**. The service rejected a single large `PolicyInputList` element at 2,000 characters. Each request therefore included **all statements together**, partitioned at statement boundaries into equivalent identity policy documents; no Deny was omitted. The BYO policies were resolved from the proposed YAML, including `!Sub`, `!Ref` and `!If`. Positive tests include every required direct and dependent authorization in the matrix except permissionless STS caller identity. No live send, tagged creation or subscription change was attempted.

Also denied: foreign region endpoints **and resource ARNs**, foreign accounts/buckets/prefixes, missing bucket owner on mutations, untagged identity mutation/association, extra or wrong tag keys, direct first-tag on a foreign untagged identity, staging writes, attachment tagging, wrong raw tags, wrong SNS protocol/endpoint, unapproved tenants/sets/reputation policy, wrong STS role/session, and classic raw send. The customer trust evaluated separately: expected principal + external ID + session + region **allowed**; absent/wrong ID, other principal, session or region **all denied**. For that simulation only, the role ARN was supplied explicitly as the simulated resource of the trust statement; no role was assumed.

**Exceptions, without widening the policies:**

1. **Identity creation:** the primary action was allowed in all five configurations; the dependent first `ses:TagResource` was denied in all five. The first-tag requirement is a policy design blocker, not a successful positive. BYO's no-op same-tag condition passed only with the existing tag actually supplied.
2. **Shared sends:** in each pool region the simulator implicitly denied `ses:SendEmail` on the tagged domain and both sets with valid `ses:TenantName`. It also denied the **unmodified live principal policy** and a minimal exact-equality control for that key. Removing the condition just to pass the simulator would permit pooled sends without a tenant. Conversely, BYO's two global-endpoint negative rows per configuration **allowed** despite a supplied `ses:MultiRegionEndpointId` and the policy requiring its absence. The simulator is not evidence of enforcement of these [documented SESv2 condition keys](https://docs.aws.amazon.com/service-authorization/latest/reference/list_sesv2.html#list_sesv2-action-SendEmail). Keep both restrictions; service-level validation remains outstanding.
3. **Feedback subscription attributes:** pool `sns:GetSubscriptionAttributes` and `sns:SetSubscriptionAttributes`, and BYO `sns:GetSubscriptionAttributes`, were implicitly denied on the documented topic resource. An isolated control also denied the literal subscription ARN. For Get the simulator returned Allow only with a wildcard grant and wildcard test resource; **that is not a reason to grant account-wide subscription access**. Historical Ohio CloudTrail has four successful reads by the pool user before live v5; that is supporting history, not proof for the candidate.

Access Analyzer returned **no findings** for the final shared policy and all three resolved BYO variants. CloudFormation `ValidateTemplate` accepted the proposal (`CAPABILITY_NAMED_IAM`); this does not deploy the stack or exercise its IAM grants. `npm run check` passed; the full isolated harness ran 99 tests, **97 passed, 2 skipped, 0 failed**.

## Boundaries not established by an Allow result

* One shared key can choose another **valid** workspace tenant or act on another **tagged** pool identity. A UUID shape is not proof of a specific workspace. IAM cannot compare the database token or derive workspace ownership from this IAM user. SES association enforcement and the app checks remain necessary. `GetEmailIdentity` on a known untagged domain intentionally remains possible. IAM globs are not DNS/hex validators.
* One deny constrains the request endpoint. A **second deny on resource ARNs**, independent of the request endpoint, limits all named SES/SNS grants to the two pool regions and account, except for those regions' AWS-owned strict reputation policy. It must be kept in sync with any future Allow. S3 bucket names also pin the requested region. SNS `SetTopicAttributes`, classic receipt rules, bucket policies, and lifecycle changes can reroute or destroy data on their authorized resources. IAM has no condition for the requested SNS policy document, classic rule name, S3 policy body or lifecycle body. Bucket ownership and `sns:Endpoint` do not make those grants harmless.
* The negative tables evaluate these **identity policies**, not all ways a compromised provisioner could gain access. In particular, a key with `s3:PutBucketPolicy` or `sns:SetTopicAttributes` can change the resource policy itself. An implicit deny in the table does not override a new same-account resource policy Allow. Isolating provisioning from day-to-day sends/reads would reduce that risk.
* `HeadBucket` is not a distinct IAM action: unprefixed enumeration of the exact Virginia BYO bucket can remain possible. **The pool has no ListBucket permission.** A destination `PutObjectTagging` check likewise also permits a direct same-tag update on a raw object. BYO SES templates keep the existing `opensend-*` contract, not an invented per-connection naming restriction. The simulator evaluates IAM actions, not MIME content; an authorized isolated BYO smoke test should include SESv2 `Content.Raw` before release, not add classic sending speculatively.
* A replacement policy and Worker must roll together **before any hosted bucket reconciliation**, including already-owned buckets outside Virginia. A customer SCP requiring the explicit `BucketOwnerEnforced` header would reject the default-only create; resolve that requirement before enabling receiving. Before any v5 release, pass `WorkspaceId` in stack quick-create, distinguish v5 from the role-only legacy workflow, and update the published template/version selector. **No publication, new AWS resources, rollout or traffic test is part of this review.**
